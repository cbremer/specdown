Proposed contract, 2026-10-31. **Docs only; all 36 acceptance cases below remain proposed, unimplemented and not passed.**

## Confirmed starting point and contract gaps

1. **Persistent identity is still a filename.** `main.js:509` calls `renderAnnotations(filename, context)`; `annotations.js:26–30,780–815` reads/writes that bucket. Transient generation/tab/root checks prevent stale actions but are not persistent document identity (`core/document-context.js:6–32`).
2. **Available provenance is not yet an authority.** Tabs retain path, requested URL or saved-copy bookmark ID (`core/state.js:14–32`), but no durable annotation document ID. Browser name/size/mtime and equal bytes cannot prove identity. Desktop FileReader ingestion bypasses the native content reply (`file-loading.js:76–98`).
3. **Reconnection and replacement semantics are incomplete.** Native MAS move evidence is discarded after path resolution; a moved folder does not prove every child's identity. Bookmark Locate/Replace changes references or content under the same bookmark ID and detaches recalled tabs (`bookmarks.js:285–344`). None of this authorizes transferring notes.
4. **The present store cannot provide compare-and-swap.** `annWriteStore` rechecks readability then calls `localStorage.setItem` (`annotations.js:388–400`); it does not compare revisions, serialize other windows, or atomically commit lineage/undo. A second writer can replace the first writer's changes.
5. **Current migration/import cannot be reused as lossless recovery.** V1 migration coerces index keys and generates fresh IDs (`annotations.js:357–384`); import merges by text/anchor/index (`:580–637`). These are not occurrence identities. The original archive must preserve duplicates independently of their projected note IDs.
6. **Backup fidelity and restore are different gaps.** Current import caps are 2 MiB, 100 documents, 500 notes/document, 2,000 notes total and 16,384 code units/note. Reading an old store does not truncate it; normal import still cannot restore every exported store. Export uses `Blob([json])` (`:438–463`), not an explicitly lossless raw encoding.
7. **The inactive inspector saves nothing.** It inventories only fully supported, bounded supplied strings; corrupt/future/ambiguous/oversized input remains raw-only in memory. Its digest addresses annotation-snapshot occurrences, never source documents. Production imports/references remain absent.
8. **Interactive association, conflict-safe undo, durable archives, privacy modes, downgrade reconciliation and platform storage guarantees remain unspecified enough to block activation.** Another detached parser/encoder would not close these gaps.

## Identity and continuity decisions

Use distinct identifiers: `storeId` for a local annotation authority, `documentId` for a collection's logical document, native `{authorityId, sourceToken}` for proven local source binding, and transient view generation/tab/root for asynchronous UI work.
Native permission grants remain separate. Imported paths, tokens, UUIDs, labels, content hashes and block fingerprints never grant access or establish a local binding.
Persist an accepted binding before advertising it as durable. Corrupt/unknown registries or failed writes yield unavailable/ephemeral identity, never silent registry recreation or a different collection.
Native token-registry persistence and annotation-store persistence are separate authorities: a token may exist without notes, but a failed annotation transaction must not report association success. No two-store atomicity is presumed.

Content digests are revision/comparison evidence, never identity or permission. Define the exact bytes/encoding hashed and retain an algorithm/version tag.
Opening a document successfully and binding its notes are separate outcomes. View content if permitted while showing an unavailable/unassigned annotation state when identity cannot be established.
Thread the immutable identity descriptor through every create/switch/close/raw/preview/watch/bookmark/session/reload route. A late reply with another source token must not rebind the current tab.
Keep current editor and asynchronous document-context guards; persistent IDs do not replace generation checks, including A→B→A and same-tab replacement.

## Association, reconnection and undo

Legacy collections enter a global **Unassigned notes** view, even when no open document shares their label. Original source provenance is unknown; an annotation-snapshot digest does not repair that missing evidence.
Preview the exact selected occurrences and the captured target document/revision before confirmation. Show matched, ambiguous, positional-only and unresolved anchors separately; do not render a speculative match as a confirmed note.
Allow per-note selection because one legacy filename bucket may already contain several documents' notes. Association copies selected occurrences into the target; it never removes the immutable archive or silently moves remaining notes.
Use snapshot digest plus occurrence address for legacy lineage: exact decoded V1 key (`01` differs from `1`), or V2 array ordinal. Repeated IDs/text remain separate. Preserve the original slice and unknown fields; do not route recovery through the existing importer.
Give each explicit operation a stable operation ID, expected store/binding revisions, source occurrence IDs, target document/revision, created-note IDs and before/after evidence. Repeating the same operation is idempotent; a deliberate second copy is a new operation.
If the same claimed backup ID contains different bytes, stage a conflict. Identical text, filename or note ID cannot authorize deduplication across independent archives/stores.
Reconnection changes a binding by an explicit operation; permission to read the selected file is a separate prerequisite. If both identities already have notes, present both collections and preserve them until the user chooses an association plan.
Undo targets that operation's changes, not an old whole-store snapshot. Remove an unchanged copied note/binding only if its current revision still equals that operation's after-revision.
If a note was edited, deleted, rebound or independently associated afterward, preserve current work and present an undo conflict/copy choice. Repeated undo is idempotent; unrelated notes and later operations remain untouched.
Retain undo lineage until an explicit retention/deletion policy is approved. Deleting an archive, deleting active notes, disconnecting a source and forgetting file permission are four different actions with distinct consequences.
Supported active projections may add derived anchors without rewriting their immutable original archive. Unknown extension payloads remain opaque; edits must preserve unaffected metadata and raw evidence.

## Persistence authority, compare-and-swap and rollback

**Activation prerequisite:** select and verify an actual transactional authority on each shipping web/desktop storage origin. `localStorage` read/check/set, storage events, BroadcastChannel, a renderer mutex or a timed lease are not compare-and-swap.
Proposed web baseline: IndexedDB read-write transactions containing the store header/revision, affected notes/collections, associations, operation ledger and activation pointer. Verify origin/partition sharing and crash/quota behavior in the supported browsers before choosing it.
Electron may use the same proven renderer-storage authority, or a main-process service backed by a real transactional database with exclusive cross-process ownership. The current synchronous `specdown-state.json` writer is not an annotation transaction service; one main window alone is not a cross-process lock.
Native source-token creation remains inside existing authorized reads and a separately owned durable registry. Do not add identity-only stat/realpath/network probes. An orphan token after annotation failure is safe; a fabricated successful binding is not.

For each mutation, the authoritative transaction reads `(storeId, revision)` and required record/binding revisions, checks caller expectations, applies all changes, records the operation ID/result and advances revision together.
Only committed success acknowledges Save/Attach/Restore/Undo. A revision mismatch returns conflict with the draft/selection intact; it never retries a stale whole-store write over newer data.
Competing tabs/windows can request work, but only the database transaction or proven exclusive coordinator owns commit. Notifications refresh views after commit; they do not grant write ownership.
Run hashing/parsing/preview outside the transaction with bounded inputs. Revalidate captured store, target binding and document revision at commit; a changed target requires a refreshed preview/confirmation.
Staged backup chunks/archive records remain unreachable from the active root until completeness and integrity are verified. Activate the verified root and operation ledger in one authoritative transaction.
On read/quota/serialization/transaction failure, abort and leave the old active root, legacy string and unrelated data intact. Preserve the draft and selected recovery plan; no success toast and no deletion to make room.
Crash before commit leaves only discardable staging; crash after commit but before acknowledgment is recovered by operation ID. Never implement rollback by restoring an older complete store over another writer's committed changes.
Cleanup may remove only staging that is unreferenced by committed roots and known not to be owned by a live operation. Retention/quota cleanup must not silently evict archives, source bindings or undo history.
Store resets/imported snapshots receive a new authority/epoch so an old revision cannot accidentally match after rollback (the ABA problem). Stale connections fail closed during schema upgrade.
Migration captures the exact legacy string but cannot atomically lock an old app's independent localStorage writes with an IndexedDB transaction. Never overwrite that key; record the captured snapshot separately and detect changed legacy text as another recovery candidate.
Do not claim that every intermediate write by an uncooperative old version can be recovered. Define mixed-version coexistence, close/reload messaging and downgrade re-import before activation; unchanged filename buckets are never blindly marked migrated forever.

## Backup/restore fidelity, bounds and privacy

**Browser-origin fidelity:** localStorage supplies a JavaScript string. Exact recovery means the same UTF-16 code units, including whitespace, escapes and lone surrogates; the original bytes of an earlier imported file are not available from that string.
`Blob([string])` performs string-to-byte conversion: a local synthetic lone-surrogate round trip changed U+D800 to U+FFFD. Thus exact in-memory getter tests do not prove an exact downloadable backup.
Use an explicitly versioned binary/code-unit encoding for that raw archive, with declared lengths and digests; keep any human-readable JSON export separately labeled. No Unicode normalization or parse/stringify round trip may replace the raw archive.
**File-origin fidelity:** when importing a backup file, byte-for-byte recovery requires preserving its supplied raw byte stream before decoding. Retain encoding/BOM/decoding diagnostics separately; never label a decoded/re-encoded string the original file.
Desktop backup files likewise require a verified byte-preserving file transport. The current desktop note store is still localStorage text; merely running on desktop does not create original note-file bytes.

Define a versioned manifest with archive kind/encoding, declared unit and byte totals, chunk count/order/length/digest, total digest, record counts, format version and store/operation provenance. Claimed IDs/digests are untrusted until verified.
Bound manifest parsing, chunk size/count, aggregate bytes, decoded code units, nesting, projection amplification, active-note count and DOM page size independently. Include encoded overhead and temporary copies in the memory budget.
Use bounded streaming/staging for imported files; verify every required chunk before activation. Reject missing, duplicate, reordered/tampered, contradictory-length or unsupported-version input without partial active restore.
The browser localStorage API returns the complete string; it is not a streaming read. The current inspector also requires that whole string and may allocate bounded projections. State this minimum memory cost and impose tested platform ceilings.
On platforms without a usable streamed writer/reader, support bounded chunk files with an explicitly tested export/reselection UX or report the size unsupported. Do not silently fall back to one unbounded Blob, FileReader or JSON parse.
Record concrete per-platform numerical ceilings and temporary-storage requirements before implementation approval. At/below the supported ceiling, grandfathered data above today's normal import limits must round-trip; above it, preserve source/staging and report unsupported capacity honestly.
Corrupt, future-schema, duplicate-key, ambiguous-version and over-inspection-limit archives may be fully restored as opaque archives without becoming active notes. The format must not require the inspector to invent an inventory/digest for those cases.
Preserve exact raw archives separately from active schema projections; a new schema never replaces the v2 key. Normal import caps remain security limits, not a license to truncate older records or claim arbitrary-size restore.
Restore into another store creates unassigned collections and local IDs/mappings. Imported authority tokens/paths do not recreate permissions or local bindings. A private same-store recovery mode still requires verified authority and conflict checks.
The recovery inventory must include active collections, unassigned archives, occurrence lineage, document/association IDs and the promised undo history. Private source-binding descriptors may be retained as quarantined recovery data; native permission grants are not part of an annotation backup.
Replacing an occupied active store is a separate explicit restore mode: first preserve a verified recovery snapshot of its current revision, then transactionally promote the validated replacement. A changed revision cancels replacement; a failed protective snapshot must stop it.
**Private recovery backup** preserves all supplied raw/opaque data and may contain private note text, paths, URLs or unknown fields. **Portable exchange** uses an explicit allowlist/redaction preview and is intentionally lossy; never call both modes lossless and sanitized.
Neither format fetches URLs or opens paths during preview/restore. Hashing private paths is not anonymization. Keep raw bindings/grants out of portable exchange and logs; source paths in a private backup remain untrusted data on restore.

## Completion and implementation gate

Before enabling any runtime migration, resolve and record: source replacement/reconnect semantics; authoritative backend and origin/partition model; supported per-platform budgets/transport; private versus exchange schemas; undo/conflict/retention behavior; mixed-version coexistence.

Record these as explicit decisions, not implementation assumptions:

- Which supported browser/Electron origins share a transaction authority, and what unsupported-storage fallback is shown?
- What are the measured manifest/chunk/aggregate/memory/disk ceilings and the exact exported-file UX on each platform?
- What counts as an explicit new revision versus a new document, and when can a source alias be retained or undone?
- What lineage/history can users delete, and how does that limit later undo or complete private recovery?

Implement an end-to-end vertical slice that captures, persists, exports, re-imports, previews, explicitly associates and undoes synthetic notes through the actual platform adapter. A pure helper with no consumer is insufficient acceptance evidence.
Fault-inject at every transaction/staging boundary and run concurrent-window/process cases using disposable profiles. Verify actual downloaded/reselected archives, not merely the string returned by a getter.
Web, direct Electron and MAS require separate runtime evidence; MAS needs the final signed sandbox/provider grant context before claiming permission/move behavior. No iOS reactivation is included.
Keep runtime identity and storage behavior unchanged while this contract is reviewed; implementation can be developed separately with disposable synthetic stores. WK-18 stays open until the full agreed matrix and independent review pass; this document is a proposal, not authorization for implementation or release.
